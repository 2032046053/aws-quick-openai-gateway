# 大文件读取与压缩循环修复

2026-11-24：已修复服务端摘要后仍超预算导致的 413/客户端反复压缩循环，默认应用于 Messages 编码路径。API Key、URL、Manual 审批模式不变。没有修改用户业务源码，也没有关闭 Claude 的上下文保护。

## 已确认的原因

真实 VS Code 日志显示：21:11、21:13、21:16 附近，读取同一个约 26 KB 的 Python 文件后，服务端虽记录 contextCompressed=true，但保留的最近完整 Read 结果仍超过固定指令之外的剩余空间，于是返回 413。Claude 将此视为请求太大，触发 reactive compact，然后重新读取文件，最终显示 Autocompact is thrashing。

这不是文件行数达到某个硬门槛：系统指令、技能参考、工具定义与当前历史共同占预算。旧压缩器为了保留最近两项事件不继续切分，返回了一个仍不符合预算的“已压缩”历史；较大的原始 Read 与 UTF-8 字节开销放大了问题。客户端扩展日志里的窗口估计也不能改变 Quick 的单消息限制。

## 新行为

1. **源头分页**：标准文本 Read 工具的 schema 同时有 file_path、offset、limit 时，未指定或过大的 limit 默认设为最多 120 行；保留路径和指定起始行。模型选小范围时保持原值。分页后的参数原样送到客户端，由客户端照常审批和执行。PDF、图片、Notebook 等二进制/专用格式和其他 MCP 工具不套用此规则。
2. **读取结果预算**：历史中的成功 Read 结果按本次剩余历史预算分配大小，最多约 12000 UTF-8 字节（剩余预算的三分之一，更紧时更小）。超长内容仅保留精确前缀和完整行，明确标注 READ EXCERPT、内容哈希及可用时的下一 offset。没有发送给模型的代码不能当作已读；编辑前须定位并重新读取精确片段。客户端原始工具结果和磁盘文件不被改写。读取错误不按成功结果处理。
3. **可靠压缩**：只选已闭合的工具组，保留最新实际任务文本、角色绑定的 system/developer 指令和最近工具组。旧记录分批摘要，每批 JSON 不超过 48000 字节。摘要长度按剩余预算动态要求，并再次校验 UTF-8 字节数；最终历史必须实际装入预算，否则明确报错，不再返回一个仍超限的“压缩成功”结果。
4. **摘要检查点**：按真实用户 principal、指令/工具版本、预算、历史组的精确哈希复用检查点。新记录追加后只总结尚未覆盖的旧组；历史改变、当前任务变化或跨用户不能误用。最多缓存 100 项内存检查点，服务重启后清空。
5. **等待与失败**：在历史摘要期间也提前发送 message_start 和 ping，正文仍只在动作完整校验后发送。固定指令/当前任务本身无法装入，或摘要无效时返回明确 invalid_request_error（非流式 422，流式 error），避免把不可解决的预算问题反复当作 413 让客户端压缩。

工具 JSON schema、审批规则、原生会话归属和错误关联 ID 保持原有机制；不会通过虚报一个更大的窗口或伪造 token 数来抑制警告。usage 仍不是实际模型账单 token。

## 使用方式

建议的工作流程是“Grep/Glob 建立位置索引 → Read 当前函数附近 30–120 行 → 局部 Edit → 运行对应测试”。需要了解全文件结构时，先搜索类/函数定义，保留简短的文件/符号/行号地图，不要通过连续读取所有页面把整份文件重新装回对话。

对于截图中已经停止的 thrashing 会话，建议新建对话，带上已有 HANDOFF.md 和当前一个子任务，不要再次附加整个源码。网关更新不会清空 VS Code 既有聊天记录；大量业务附件和手工粘贴的代码也不会被擅自删除。编辑器的源码文件与之前已执行的修改保持原样。

环境变量（重启 quick-codex 后生效）：

```text
QUICK_CLAUDE_READ_LINES=120
```

允许 1–5000 的整数；设 0 关闭新增的 Read 分页/结果节流提示，保留可靠压缩逻辑。增加页大小会增加再次超预算的风险。QUICK_CLAUDE_AUTO_COMPACT=0 则关闭服务端历史摘要，仍可使用分页；不建议靠关闭所有压缩来处理长任务。
